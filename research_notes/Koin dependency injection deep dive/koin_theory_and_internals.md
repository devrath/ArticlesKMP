# Koin: Core Theory, Philosophy, and Runtime Internals

## What problem does DI solve, and why was Koin created? What is Koin's stated philosophy/goals?

### Takeaway
Dependency Injection (the general pattern Koin implements) separates object construction from object use so classes don't instantiate their own collaborators; Koin's specific pitch is to deliver this for Kotlin with minimal setup, no annotation-processing build step (in its classic DSL form), and a container built from "pure Kotlin" functional constructs rather than Java-reflection-heavy frameworks. Koin describes itself as "a pragmatic lightweight dependency injection framework for Kotlin developers" — "a DSL, a light container and a pragmatic API."

### Cited Findings
- Koin's own framing: "Koin is a pragmatic lightweight dependency injection framework for Kotlin developers, developed by Kotzilla and open-source contributors. Koin is a DSL, a light container and a pragmatic API." — [Koin docs/mirrors](https://awesome.ecosyste.ms/projects/github.com%2Finsertkoinio%2Fkoin-getting-started)
- An early/historical framing of Koin's design claim, repeated across mirrors: "written in pure Kotlin, using functional resolution only: no proxy, no code generation, no reflection." — [Koin mirror text, cited via search](https://en.paradigmadigital.com/dev/dependency-injection-with-koin/); same phrase also surfaced in [a Medium retrospective](https://medium.com/the-kotlin-chronicle/advocating-for-and-against-koin-2281869e892b)
- Rationale given by a third-party technical article: code generation and reflection (as used by other DI frameworks) can hurt performance, especially on resource-constrained mobile devices, and avoiding code generation also avoids long compile times — cited as a design goal behind Koin. — [Paradigma Digital, "Dependency injection with Koin"](https://en.paradigmadigital.com/dev/dependency-injection-with-koin/)
- Koin's own comparison page against Hilt/Dagger states Koin's goals explicitly: less setup/boilerplate (no `@Inject` constructors, no `@Binds` modules, no `@AndroidEntryPoint`), reach beyond Android via Kotlin Multiplatform, runtime flexibility (loading/unloading modules at runtime for feature flags or plugin architectures — something Hilt cannot do post-compilation), and a choice between a DSL approach and an annotations approach. — [insert-koin.io, "Koin vs Hilt"](https://insert-koin.io/docs/intro/koin-vs-hilt)
- The same page acknowledges Hilt's strengths in contrast: complete build-time graph verification, no runtime lookup overhead, Java support, official Android guidance/ecosystem adoption, and detailed compiler error paths. — [insert-koin.io, "Koin vs Hilt"](https://insert-koin.io/docs/intro/koin-vs-hilt)
- A November 2025 droidcon/ProAndroidDev article pushes back on the "no reflection" framing, arguing Koin builds its dependency graph at runtime using the Kotlin DSL and reflection to infer constructor parameters, and that there is no code generation in the classic DSL path — only runtime lookups. — [droidcon, "Hilt vs Koin: The Hidden Cost of Runtime Injection"](https://www.droidcon.com/2025/11/26/hilt-vs-koin-the-hidden-cost-of-runtime-injection-and-why-compile-time-di-wins/) / [ProAndroidDev mirror](https://proandroiddev.com/hilt-vs-koin-the-hidden-cost-of-runtime-injection-and-why-compile-time-di-wins-3d8c522a073b)
- Koin's documentation on the "classic" lambda DSL vs. the newer constructor-reference DSL: `singleOf`/`factoryOf`, built on `inline fun <reified R>` constructor references, are described as "reflection-free dependency injection" — implying the classic lambda form (`single { MyClass(get()) }`) is *not* literally reflection, but resolves generic types via Kotlin's `reified` type parameters baked into inlined functions rather than runtime `Class<T>` reflection. — [Koin 4.1.0 docs mirror, "constructor-reference"](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/constructor-reference.md)
- Koin's docs explicitly mark the older "Koin Reflection DSL" as deprecated in favor of the "Koin Autowire DSL" (the KSP/compiler-plugin-backed path). — [Koin docs, "dsl-update"](https://insert-koin.io/docs/reference/koin-core/dsl-update/)
- Koin now also offers a compile-time-checked path: the Koin Compiler Plugin, which Koin's docs say generates constructor wiring and lets module validation (the Verify API) and Koin Annotations (via KSP) run as "first-class citizens, equally powerful," narrowing — but not eliminating — the runtime/compile-time gap with Hilt. — [insert-koin.io, "Koin vs Hilt"](https://insert-koin.io/docs/intro/koin-vs-hilt)

### Inferences
- Koin's "no reflection" claim is best understood narrowly: Koin avoids Java-style runtime `Class`-based reflection and build-time annotation processing for its *default/classic* DSL, substituting Kotlin inline + reified generic functions and plain higher-order-function (lambda) definitions evaluated at runtime. Whether this counts as "reflection" is a semantic dispute between Koin's own marketing language and outside technical writers — flag this when citing Koin's "no reflection" claim verbatim.
- The project appears to have evolved: the original pitch (pure functional resolution, zero codegen) is increasingly supplemented by an *optional* compile-time layer (Koin Annotations / KSP / Compiler Plugin) that brings Koin closer to Hilt-style build-time safety, while keeping the runtime DSL as the lower-ceremony default. Report should distinguish "classic Koin" (pure runtime DSL) from "Koin + Annotations/Compiler Plugin" (hybrid).

## Koin's design: DSL + service-locator-like runtime resolution vs. Dagger/Hilt's compile-time codegen

### Takeaway
Koin keeps the dependency graph as a runtime container: modules register "definitions" (lambdas describing how to build a type) in a registry, and calls to `get()`/`inject()` look that registry up by type (and qualifier) at the moment of resolution — the classic service-locator shape — whereas Hilt/Dagger generate Java/Kotlin source at build time (factories, binding/provider code) so the app never performs a runtime registry lookup.

### Cited Findings
- Koin's own comparison: Hilt "generates the whole graph as Java source at build time, so the app calls generated factories directly with no lookup," while Koin "keeps the graph in a runtime container," registering definitions at startup and resolving them by type. — [insert-koin.io, "Koin vs Hilt"](https://insert-koin.io/docs/intro/koin-vs-hilt)
- Hilt relies on annotation processing (KSP or kapt) plus the Hilt Gradle plugin; Koin's optional Compiler Plugin generates constructor wiring, but the base DSL/Classic approach needs no build plugin at all. — [insert-koin.io, "Koin vs Hilt"](https://insert-koin.io/docs/intro/koin-vs-hilt)
- Koin supports loading and unloading modules at runtime (including "lazy modules"), which Hilt's compiled graph cannot do post-build — cited explicitly as a Koin-only capability ("Load modules at runtime | ✅ loadKoinModules() | ❌ Not possible"). — [insert-koin.io, "Koin vs Hilt"](https://insert-koin.io/docs/intro/koin-vs-hilt)
- A Kotlin-community Slack discussion on "Dagger vs Hilt vs Koin vs Metro" frames the distinction as: `by inject()`/`get()` style calls are "service locator," whereas constructor injection is "more traditional DI" — and notes Hilt itself has service-locator-style call sites at integration boundaries (e.g. `hiltViewModel()`), meaning the service-locator-vs-DI line is about *where* lookups happen, not a clean binary between the frameworks. — [kotlinlang Slack via search](https://slack-chats.kotlinlang.org/t/33094191/dagger-vs-hilt-vs-koin-vs-metro-vs-lt-what-comes-next-gt-ser)
- Comparison articles consistently describe Dagger/Hilt's build-time codegen as producing "factories, providers, and dependency trees before the app ever runs," credited with catching broken graphs at compile time and avoiding runtime resolution cost; Koin is described as "retrieving dependencies dynamically through a centralized registry," with one source attributing a (relatively) slower startup to Koin vs. Dagger/Hilt as a tradeoff. — [DEV Community comparison](https://dev.to/mikkelofficial7/koin-vs-dagger-2-vs-hilt-which-one-should-we-use-1e0n); [ProAndroidDev benchmark piece](https://proandroiddev.com/benchmarking-koin-vs-dagger-hilt-in-modern-android-development-2024-ff7bb40470df)

### Inferences
- "Service-locator-like" is an apt characterization specifically because `get()`/`by inject()` calls pull from a global or scoped registry by *type* at the call site, rather than dependencies being *pushed in* via a statically-generated constructor-call graph the way Dagger/Hilt's generated `Factory`/`Provider`/`Component` classes do. The report should present this as the key structural difference, not merely a "runtime vs compile-time" slogan.
- Koin's runtime flexibility (hot-swappable modules, feature-flag-driven definitions) is the direct benefit that falls out of keeping the graph mutable at runtime — this is the main argument Koin's own docs make for choosing it over Hilt despite giving up build-time graph verification by default.

### Gaps
- I did not find the exact concrete performance numbers from the cited 2024 ProAndroidDev Koin-vs-Hilt benchmark (startup time deltas, DI resolution time) within the fetched summary — only that it compares Koin 4.0.1-Beta1 vs Hilt 2.52. A follow-up fetch of that article would be needed for hard numbers.

## Core internal classes/concepts: KoinApplication, Koin, GlobalContext, Module/ModuleDefinition, InstanceFactory variants, registry/IndexKey, lookup by type+qualifier

### Takeaway
`startKoin { }` builds a `KoinApplication` (container configuration) and registers it in `GlobalContext` so static `get()`/`inject()` calls can reach it; the actual container object is a `Koin` instance reachable via `KoinComponent.getKoin()`, holding a registry of `single`/`factory`/`scoped` definitions each wrapped in an `InstanceFactory` subtype, looked up by a key combining type and optional qualifier. I could not independently confirm the exact `IndexKey` implementation details from primary source in this session — flagged as a gap below.

### Cited Findings
- `KoinComponent` is described in Koin's own docs as "an interface that gives a class access to the Koin container, so it can call `get()` and `by inject()`." Its only member is `getKoin()`, which returns the `Koin` instance; by default this returns "the global container started with `startKoin`." If `startKoin` was never called, `get()` throws `IllegalStateException`. — [insert-koin.io, "Koin Component"](https://insert-koin.io/docs/reference/koin-core/koin-component)
- `get()` and `inject()` are extension functions living in package `org.koin.core.component`, taking a qualifier and a parameters block; `get()` resolves eagerly (at the point it's called / object construction time), `by inject()` resolves lazily (deferred to first property access). — [insert-koin.io, "Koin Component"](https://insert-koin.io/docs/reference/koin-core/koin-component)
- `KoinScopeComponent` is the scope-aware variant: its `get()`/`inject()` resolve against that component's own `scope` rather than the global container. — [insert-koin.io, "Koin Component"](https://insert-koin.io/docs/reference/koin-core/koin-component)
- `startKoin { }` is "the main entry point to launch [the] Koin container"; it "create[s] a `KoinApplication` container configuration and register[s] it in the `GlobalContext`" so the static `GlobalContext` API (and thus unscoped `get()`/`inject()`) works; `startKoin` cannot be called more than once — later module loading goes through `loadKoinModules()` instead. `koinApplication { }` (lowercase) creates a *standalone* (non-global) instance instead. `stopKoin()` stops/clears the `GlobalContext`. — [insert-koin.io, "Start Koin"](https://insert-koin.io/docs/reference/koin-core/start-koin) (via search synthesis)
- `single`/`factory` DSL functions accept an optional qualifier parameter (default `null`), typically supplied via `named("...")`; this qualifier plus the type form the lookup key, e.g. `single<Database>(named("local")) { LocalDatabase() }` must be retrieved with the same qualifier. — [Habr article on Koin qualifiers, via search](https://habr.com/en/articles/599177)
- Indirect evidence of an internal index/key structure: a reported real-world error states "the InstanceRegistry already contains index 'Factory'" when two differently-nested classes sharing the simple name `Factory` were both bound as singletons — implying Koin derives a registry index key that can collide on (at least) simple class name, consistent with a type+qualifier based `IndexKey`. — [Kotlin Slack thread, via search](https://slack-chats.kotlinlang.org/t/499823/when-binding-two-singletons-like-this-single-someclass-facto)
- `InstanceFactory<T>` is documented (in the Dart/Flutter port of Koin, which mirrors the Kotlin design) as "a Koin instance holder that creates, gets, and releases an instance of a given definition"; `SingleInstanceFactory<T>` is "a single-definition instance holder," constructed from a `Koin` instance and a provider/definition. — [pub.dev Koin (Dart) docs](https://pub.dev/documentation/koin/0.15.0-nullsafety.0/instance_factory/InstanceFactory-class.html), [SingleInstanceFactory docs](https://pub.dev/documentation/koin/0.15.0-nullsafety.0/instance_factory/SingleInstanceFactory-class.html) — **caveat: this is the Dart port's API documentation, used here only as a structural analog; I could not load the actual Kotlin source file (404s, see Gaps) to confirm identical class/method names in current Koin-Kotlin.**
- A real concurrency bug report on `SingleInstanceFactory` (Kotlin, JVM) confirms the class exists in current Koin-Kotlin and that its `create` path was previously synchronized; a maintainer commented that "`create` is just used by `get`, so synchronization could be removed from the create path," referencing GitHub PR `InsertKoinIO/koin#914`. This corroborates: (a) a `SingleInstanceFactory` class exists with `create()` and `get()` methods, (b) `get()` is the entry point that triggers `create()` when no cached instance exists yet (lazy-on-first-get for a given single, modulo `createdAtStart`). — [kotlinlang Slack thread, via search](https://slack-chats.kotlinlang.org/t/499782/hi-there-i-think-i-just-found-a-concurrency-issue-in-koin-af)

### Inferences
- The resolution chain is: `KoinComponent.getKoin()` → `Koin` instance → (its internal `InstanceRegistry`/`ScopeRegistry`) → look up by `IndexKey` (type [+ qualifier]) → the matching `InstanceFactory` subtype's `get()` method → returns cached instance (`SingleInstanceFactory`) or builds a new one (`FactoryInstanceFactory`) or resolves within/creates a scope-bound instance (`ScopedInstanceFactory`). This is inferred from the combination of official docs (`KoinComponent`/`get()`/`inject()` behavior) and the structural evidence above (the Dart port's class docs plus the Kotlin concurrency bug report) rather than read directly off the current Kotlin source — treat exact method names (`create`, `get`, `drop`/`release`) as the best, but not fully source-verified, approximation.
- `GlobalContext` functions as a process-wide holder of exactly one live `Koin` container (set by `startKoin`, cleared by `stopKoin`); `koinApplication { }` bypasses `GlobalContext` entirely for isolated/test containers — consistent with Koin's "Context Isolation" feature referenced (but not detailed) by the Koin Component docs page.

## Building/traversing the dependency graph at startup: eager vs. lazy, when singles are created, circular dependency detection

### Takeaway
By default Koin definitions are **lazy**: a `single { }` is only actually instantiated the first time it's resolved via `get()`/`inject()`, not at `startKoin` time — unless explicitly marked `createdAtStart = true` (or the whole container is built with `createEagerInstances = true`), in which case Koin eagerly instantiates those flagged singles right after modules load. Circular dependencies are **not statically detected** by the classic runtime DSL by default — a documented runtime error ("Circular dependency detected") occurs during resolution unless you break the cycle with lazy injection/refactoring, or opt into the newer Koin Compiler Plugin, which does catch cycles at compile time.

### Cited Findings
- `single` accepts a `createdAtStart = true` flag to mark a singleton for startup creation, letting critical services be built eagerly while other singletons stay lazy. — [Koin docs mirror (tessl.io, Koin 4.1.0 "application")](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core/4.1.0/files/docs/application.md)
- Actually creating the flagged eager instances happens via `createEagerInstances()` called on the application builder; a `koinApplication(createEagerInstances: Boolean = true)` constructor parameter also exists to trigger this at construction time. — [Koin docs mirror (tessl.io)](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core/files/docs/application.md)
- Real-world reports: a developer found `createdAtStart` alone did nothing until `createEagerInstances()` was explicitly invoked; another reported that modules added later via `loadKoinModules()` (after the initial `startKoin`) did **not** get their `createdAtStart` singles eagerly created — only `startKoin`'s own initial modules did — requiring a manual re-call of `createEagerInstances()` as a workaround. This remained unresolved/unconfirmed as bug-vs-intended-behavior in the thread. — [kotlinlang Slack thread #1](https://slack-chats.kotlinlang.org/t/15626755/hey-guys-i-face-a-problem-with-creation-of-eager-instances-b?t=v2); related [GitHub issue #1318](https://github-redirect.dependabot.com/InsertKoinIO/koin/issues/1318)
- Koin's troubleshooting docs state that without the Koin Compiler Plugin, a dependency cycle "fails at startup with a runtime error," with documented error text "Circular dependency detected," and recommend fixing it via lazy injection (`inject()` instead of `get()`) or refactoring the dependency structure. — [insert-koin.io troubleshooting docs, via search](https://insert-koin.io/docs/reference/koin-core/troubleshooting)
- The Koin Compiler Plugin is documented to detect circular dependencies **at compile time**, catching the cycle before the app ever runs — a build-time safety net layered on top of the runtime-resolved core. — [insert-koin.io troubleshooting docs, via search](https://insert-koin.io/docs/reference/koin-core/troubleshooting)
- A Koin maintainer, in a Kotlin Slack thread, stated there *was* a cycle-dependency detector in Koin 2.1.x that was removed "for performance consideration," adding it "may be worth reconsidering later" — meaning older Koin versions actively detected cycles at runtime (likely via a resolution stack / "currently resolving" set) and this was deliberately dropped in favor of raw stack-overflow-style failure for performance. — [kotlinlang Slack thread](https://slack-chats.kotlinlang.org/t/499636/hello-i-m-having-this-stacktracke-while-i-m-trying-to-work-w)
- A third-party IDE plugin (Kotzilla's Koin plugin for IntelliJ/Android Studio) advertises detecting circular references (among other config issues) as a static-analysis/tooling feature outside the runtime framework itself. — [Product Hunt listing, via search](https://ship.producthunt.com/posts/koin-plugin-for-intellij-android-studio)

### Inferences
- Default behavior (no `createdAtStart`, no Compiler Plugin) is: modules are *registered* (their lambda-based definitions stored in the registry) synchronously during `startKoin { modules(...) }`, but no actual instance construction happens until the first `get()`/`inject()` resolution of each `single`/`factory`/`scoped` binding — this is the standard "lazy by default" DI container behavior, confirmed by the explicit existence of an opt-in `createdAtStart`/`createEagerInstances()` mechanism (which would be redundant if everything were already eager).
- Without the removed 2.1.x-era cycle detector, a circular dependency today most likely manifests as infinite mutual recursion inside the `get()`→`create()` resolution chain, surfacing either as a `StackOverflowError` or as the documented "Circular dependency detected" runtime exception — the exact current mechanism (explicit check vs. relying on native stack overflow) is not fully confirmed from primary source in this pass (see Gaps).
- The `loadKoinModules()` + eager-instance interaction bug reports suggest Koin's "build the graph" step is genuinely incremental/mutable at runtime (consistent with its service-locator design), rather than a single frozen pass — reinforcing the "runtime container, not a build-time fixed graph" theme from the philosophy section.

### Gaps
- I did not confirm, from Koin's current (2025/2026) Kotlin source, whether "Circular dependency detected" is thrown by an explicit resolution-stack check (e.g., a `HashSet<IndexKey>`/call-stack guard inside `InstanceFactory.get()`/`create()`) or whether it's simply a `StackOverflowError` that Koin's docs loosely describe with that phrase. The maintainer's Slack comment about removing a 2.1.x detector "for performance" suggests the former check may no longer exist, making the latter (raw stack overflow) more likely — but this is inference, not confirmed fact. A direct read of current `InstanceFactory.kt`/`Scope.kt` source (blocked by 404s in this session) would resolve it.
- Did not verify the current default value of `koinApplication`'s `createEagerInstances` parameter across Koin versions, nor whether `startKoin { }` (vs `koinApplication { }`) differs in default eager-creation behavior.

## Runtime exceptions for missing/ambiguous bindings, and `checkModules`/`verify()` for earlier error-catching

### Takeaway
A missing binding at resolution time throws `NoBeanDefFoundException` (historically; naming may have evolved in current Koin major versions — not confirmed from primary docs in this pass); Koin offers two different "catch it before production" mechanisms — the older, more dynamic `checkModules()` (runs a sandboxed instantiation pass inside a test-time `koinApplication { modules(...); checkModules() }`) and the newer, static `verify()` (a JUnit-callable extension on a `Module` that cross-checks constructor parameter types against declared definitions without instantiating anything), the latter reported as superseding/deprecating the former per a maintainer comment.

### Cited Findings
- The historically well-documented runtime exception for an unresolved dependency is `NoBeanDefFoundException` ("check your module definitions"), seen across many real-world Stack Overflow / Slack reports spanning Koin 0.9.x through more recent versions; common root causes cited: binding a concrete class but requesting its interface (or vice versa), missing manual registration for library-provided types (e.g. `WorkManager`), typos (`module` vs `modules` in test setup), and scope-registry definitions not being visible in the expected scope. — [Kotlin Slack thread, Koin 0.9.1→0.9.2 upgrade](https://slack-chats.kotlinlang.org/t/13842190/hi-i-cannot-update-my-project-from-koin-0-9-1-to-0-9-2-due-t); [Slack thread](https://slack-chats.kotlinlang.org/t/22694341/i-am-getting-org-koin-core-error-nobeandeffoundexception-no-); [Stack Overflow via Kiwix mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/51195471/koin-android-org-koin-error-nobeandeffoundexception); [Stack Overflow via Kiwix mirror #2](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/57535800/koin-nobeandeffoundexception-check-your-module-definitions)
- `verify()`: an extension function on a Koin `module`, JVM-only, that "inspects the module's constructor classes and cross-checks them against the declared definitions to confirm that each dependency has a matching component." If a dependency is missing, it throws `MissingKoinDefinitionException`. It runs as a plain JUnit test, with no mocks/stubs required. Introduced basic form tagged Koin **3.3**; the `injections`/`injectedParameters()` parameter-handling addition tagged Koin **4.0**. — [insert-koin.io, "Verify" (4.0 docs)](https://insert-koin.io/docs/4.0/reference/koin-test/verify)
- `verify()` parameters: `extraTypes` lists types the configuration uses but never declares directly (docs' examples: `SavedStateHandle`, `WorkerParameters` — injected externally rather than defined via `single`/`factory`); listed types are treated as present for every definition's check. `injections` (`injectedParameters(definition<Type>(Class1::class, ...))`) handles definitions that take parameters via `parametersOf`, which otherwise fail verification since the parameter's type has no definition of its own. — [insert-koin.io, "Verify"](https://insert-koin.io/docs/4.0/reference/koin-test/verify)
- `checkModules()`: runs inside `koinApplication { modules(...); checkModules() }` — described as a "sandbox run" that actually launches the modules and tries to execute each possible definition dynamically (as opposed to `verify()`'s static constructor/metadata inspection). Missing values needed for the run can be supplied via `withInstance()` / `withParameter(s)`. — [insert-koin.io docs via search synthesis](https://lts.insert-koin.io/docs/reference/koin-test/checkmodules); [Kotlin Slack thread comparing the two](https://slack-chats.kotlinlang.org/t/13841383/could-you-run-a-test-that-checks-your-modules-for-you-test-f?t=v2)
- A Kotlin Slack thread states `checkModules` is "deprecated in favor of `verify`" per community discussion, though no official Koin changelog/release-note confirmation of this deprecation was located in this research pass. — [Kotlin Slack thread](https://slack-chats.kotlinlang.org/t/13841383/could-you-run-a-test-that-checks-your-modules-for-you-test-f?t=v2)
- A caution from the same thread: one user reported scenarios where `verify()` should have failed (e.g., a genuinely broken binding) but did not — i.e., `verify()`'s static check has known gaps and should not be assumed to catch every category of misconfiguration. — [Kotlin Slack thread](https://slack-chats.kotlinlang.org/t/13841383/could-you-run-a-test-that-checks-your-modules-for-you-test-f?t=v2)

### Inferences
- `verify()` and `checkModules()` are Koin's answer to the central weakness of a runtime-resolved DI container: since there's no compiler pass over the graph, Koin instead offers *test-time* tooling (run inside ordinary JUnit tests, not at app startup) that approximates compile-time checking — `verify()` via static metadata inspection (fast, no side effects, but blind to certain runtime-only wiring), `checkModules()` via an actual sandboxed instantiation pass (slower/heavier but exercises real construction code, including whatever side effects that entails).
- The move from `checkModules()` toward `verify()` mirrors the project's general move toward "safety without giving up the runtime model" — using Koin Annotations/KSP metadata (where available) to let `verify()` reason about constructors without invoking them.

### Gaps
- Did not confirm whether `NoBeanDefFoundException` is still the current (Koin 4.x, late-2025/2026) exception name, or whether it has been renamed/replaced (e.g., to something under `org.koin.core.error`, possibly `NoDefinitionFoundException` per one search query's phrasing, though that search found no hits confirming that name exists). **This should be verified directly against current Koin release notes/source before stating a definitive current exception class name in the final report** — treat `NoBeanDefFoundException` as the well-documented *historical* name and flag uncertainty about whether it persists unchanged into the current major version.
- Did not find an official Koin changelog entry confirming `checkModules()`'s deprecation status — only a community (non-maintainer-sourced in the retrieved snippet) claim.
- Did not enumerate other possible runtime exceptions (e.g., for ambiguous/duplicate bindings at module-definition time, such as the `InstanceRegistry already contains index 'X'` error referenced earlier) as a formal exception type/class name — only observed as informal error text in a bug report.

## How `get()`, `inject()`, and `by koin.inject()` work step by step; how scopes work internally

### Takeaway
`get()` is an eager, synchronous call that immediately walks `KoinComponent.getKoin()` → the container's registry → the matching `InstanceFactory` → returns (or builds) the instance; `by inject()` is a Kotlin property delegate that defers that exact same `get()` call until the property is first read (via `lazy { getKoin().get(...) }`-style semantics per community description). Scopes add an intermediate `Scope` object — identified by a `ScopeID` (a `String`) plus a qualifier — that holds `scoped` definitions tied to some lifecycle-owning "source" object, is created via `Koin.createScope(scopeId, qualifier, source)` / `getOrCreateScope` / `getScope`, can be linked to other scopes via `linkTo()`/`unlink()` so one scope's resolution can fall through to another's definitions, and must be explicitly ended via `scope.close()` (or `Koin.deleteScope(scopeId)`) to release its cached instances.

### Cited Findings
- `KoinComponent.getKoin()` returns the `Koin` instance (global by default, from `GlobalContext`, unless overridden); `get()`/`inject()` are extension functions on `KoinComponent` in `org.koin.core.component`, each taking an optional qualifier and a `parameters` block. — [insert-koin.io, "Koin Component"](https://insert-koin.io/docs/reference/koin-core/koin-component)
- `get()` retrieves the instance "immediately" (eager, at the point of the call / at the owning object's construction); `by inject()` is the officially recommended form for a property that should be "lazy evaluated," deferring retrieval to first access. — [insert-koin.io docs, via search](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-js/files/docs/dependency-injection.md)
- A technical blog (describing Dagger/Hilt vs Koin internals) states `by inject()` "calls get() lazily under the hood," i.e. the delegate simply wraps a deferred `get()` call rather than implementing separate resolution logic — consistent with Kotlin's standard `lazy { }` delegate pattern. — [loctra0602 blog, "How Dagger, Hilt, and Koin differ under the hood"](https://loctra0602.blogspot.com/2021/07/how-dagger-hilt-and-koin-differ-under.html)
- `KoinScopeComponent` is the scope-aware analog of `KoinComponent`: its `get()`/`inject()` resolve against that component's own `scope` property rather than the global/unscoped container; the documented pattern is to override `scope` with `createScope(this)` so the scope's lifetime is tied to the owning class instance. — [insert-koin.io, "Koin Component"](https://insert-koin.io/docs/reference/koin-core/koin-component)
- `Scope` (per a Koin-core 4.1.0 reference) has a `scopeQualifier`, an `id` of type `ScopeID`, an `isRoot` flag, a reference to the owning `Koin` instance, and a `close()` method; `ScopeID` is a type alias for `String`. — [Koin docs mirror (tessl.io, koin-core 4.1.0 scope-management)](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/scope-management.md)
- `Koin` exposes `createScope(scopeId, qualifier, source)`, `getOrCreateScope(...)`, and `getScope(...)` to obtain `Scope` instances; the `source` parameter links the scope to an external lifecycle owner (e.g. an Android `Activity`) for cleanup purposes. — [Koin docs mirror (tessl.io)](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/scope-management.md)
- Official LTS docs instruct calling `scope.close()` once a scope is finished with, to release its held instances; the 4.1.0 mirror additionally documents a `Koin.deleteScope(scopeId)` that both deletes the scope and closes its instances. — [Koin docs, scopes (LTS)](https://lts.insert-koin.io/docs/reference/koin-core/scopes); [Koin docs mirror, scope-management 4.1.0](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/scope-management.md)
- Scopes can be explicitly linked with `linkTo(...)` / unlinked with `unlink(...)`, allowing one scope to fall through and resolve definitions declared in another scope. — [Koin docs mirror (tessl.io)](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/scope-management.md)
- Caveat flagged directly by the research itself: official LTS docs and the 4.1.0 tessl mirror "differ in some details, such as whether a `ScopeID` is a typealias for `String` and how the `close`/`deleteScope` behaviour is described" — i.e., scope-management API details may have shifted between Koin minor/major versions, so version-pin any scope internals claims in the final report.
- Historical/older API note: some older example code uses `newScope` and `koin.createScope<A>()` (a reified generic form) — the current official docs page apparently still shows some of this older syntax per the search summary, meaning readers following tutorials predating a given Koin version may see different scope-creation call signatures than current best practice. — [kotlinlang Slack thread on Koin 2.0.1 scopes, via search](https://slack-chats.kotlinlang.org/t/499957/i-m-trying-to-understand-scopes-in-koin-2-0-1-and-why-they-h)

### Inferences
- Step-by-step for `get()`: (1) caller's class implements `KoinComponent` (or receives `Koin`/`Scope` directly); (2) call `get<T>(qualifier, parameters)`; (3) internally calls `getKoin()` to obtain the `Koin` container; (4) the container (or, for scope-aware components, the `Scope`) looks up the registered definition keyed by `T` + qualifier; (5) the matching `InstanceFactory` subtype either returns a cached instance (`SingleInstanceFactory`, after first creation) or invokes the stored definition lambda to build a new instance (`FactoryInstanceFactory` on every call; `ScopedInstanceFactory` once per scope instance). This synthesizes the `KoinComponent` docs with the `InstanceFactory`/`SingleInstanceFactory` evidence from the previous section — see that section's Gaps for what remains unverified against primary source.
- Step-by-step for `by inject()`: identical lookup chain to `get()`, except wrapped in a Kotlin property delegate (effectively `lazy { get<T>(qualifier, parameters) } `), so steps (3)-(5) above are deferred until the delegated property is first read rather than running at the point `by inject()` is declared.
- Scope lifecycle mirrors the global container's own `startKoin`/`stopKoin` pattern at a smaller granularity: `createScope`/`getOrCreateScope` is analogous to registering a mini sub-container tied to a `source` object's lifetime, and `close()`/`deleteScope` is analogous to `stopKoin()` for that sub-container — releasing cached `scoped` instances so they're rebuilt on next scope creation.

### Gaps
- Did not obtain primary-source confirmation (actual Kotlin source file) of the `Scope` class's internal instance cache structure (e.g., whether it holds its own mini `InstanceRegistry` or delegates back to the parent `Koin`'s registry filtered by scope ID) — this is inferred from documented behavior, not read directly from `Scope.kt` (blocked by the same GitHub-fetch issues noted earlier).
- Did not confirm whether current Koin (4.x) still supports the reified `koin.createScope<A>()` form alongside `createScope(scopeId, qualifier, source)`, or whether one has been deprecated in favor of the other — flagged as a version-drift risk in the findings above.
- No primary-source detail found on exactly how `ScopeRegistry` (the container-level registry of all open `Scope` instances, referenced only indirectly) stores/retrieves scopes by `ScopeID`, or whether/how garbage-collection of the `source` object interacts with explicit `close()` calls.
