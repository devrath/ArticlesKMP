# Koin Support for Kotlin Multiplatform (KMP)

## Why is `koin-core` pure Kotlin with no Android/JVM-specific dependencies — what does this mean technically, and why does it let Koin compile to Native/JS/Wasm?

### Takeaway
Koin's original design principle (true through the 2.x/3.x era) is "pure Kotlin, functional resolution only — no proxy, no code generation, no reflection," which is precisely what makes `koin-core` portable to every Kotlin compilation target (JVM, Android, Kotlin/Native, Kotlin/JS, Kotlin/Wasm). As of Koin 4.2 (RC/beta cycle active in late 2025), Koin has *added* an optional K2 Compiler Plugin for compile-time graph validation, so the "no code generation" part of the old claim no longer fully holds for projects that opt into the plugin — but the DSL-based runtime core remains reflection-free and platform-API-free.

### Cited Findings
- An older Koin README (fork snapshot, Koin 2.0.0-beta-1) states Koin is "written in pure Kotlin, using functional resolution only: no proxy, no code generation, no reflection." — [erickok/koin README mirror](https://github.com/erickok/koin)
- A Packt Publishing book on Android/Kotlin DI repeats this characterization: Koin "requires no code generation and is built based on Kotlin's functional extensions." — [Packt: Dependency Injection with Dagger, Hilt and Koin](https://www.packtpub.com/en-id/product/how-to-build-android-apps-with-kotlin-second-edition-16-9781837634934/chapter/chapter-13-dependency-injection-with-dagger-hilt-and-koin/koin)
- The current GitHub repo "About" section now reads "Koin is a pragmatic, lightweight dependency injection framework for Kotlin developers" and separately states "Koin is now compile-safe thanks to the Koin Compiler Plugin," which verifies the dependency graph at compile time so "missing bindings and misconfigured modules are caught by the compiler instead of crashing at runtime." — [InsertKoinIO/koin on GitHub](https://github.com/InsertKoinIO/koin)
- The Koin Compiler Plugin requires the K2 compiler (Kotlin 2.3.x+) and Koin 4.2.0-RC2+; plugin release 0.4.0 validates the entire dependency graph at compile time, and plugin 1.2.1 targets Koin 4.2.0+ with Kotlin 2.3.20–2.4.20. — [koin-compiler-plugin releases via newreleases.io](https://newreleases.io/project/github/InsertKoinIO/koin/release/4.2.0-RC2)
- Official docs state: "`koin-core` and the Compiler Plugin support every Kotlin target," explicitly listing Android, iOS (iosArm64/iosX64/iosSimulatorArm64), JVM (desktop/server), JS and Wasm (js, wasmJs), and macOS/Linux/Windows via Kotlin/Native. — [Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)
- Koin 3.0.1's release notes announced the core package became "compatible with Multiplatform," with core functions usable from the multiplatform side (i.e., multiplatform support was a later addition, not present from Koin 1.x). — [Koin 3.0.1 Release & 2.x Redeploy blog](https://blog.insert-koin.io/koin-3-0-1-release-2-x-redeploy-856c2cc6edec)

### Inferences
- "No reflection" is the load-bearing technical property for cross-target compilation: `java.lang.reflect`/annotation-processor-based reflection (as used by Dagger/Hilt at points, or older service-locator frameworks) does not exist on Kotlin/Native or Kotlin/Wasm runtimes, so any DI framework that depends on JVM reflection cannot target those platforms at all. Koin's DSL (`module { single { ... } }`) resolves dependencies via plain Kotlin lambdas/functions stored in a registry and looked up by type information Kotlin itself tracks (`KClass`), not via `Class.forName`/dynamic proxies — this is why it was portable to Kotlin/Native and Kotlin/JS even before Multiplatform was an explicit goal.
- The new Compiler Plugin is IR-based (K2 compiler plugin), not KSP/kapt annotation processing — it still does not rely on JVM runtime reflection, so cross-target compatibility is preserved even as "no code generation" becomes technically inaccurate for the plugin-enabled path. This is an important nuance for an interview: the "no reflection" claim survives into 2025–2026, but "no code generation/no proxy" is now only true of the pure-DSL (non-plugin) usage mode.

### Gaps
- No official Koin doc page explicitly restates the "no reflection, no proxy" phrasing in current (4.x) wording — this phrasing is only confirmed from older 2.x-era README snapshots and a secondary book source; the current official site was not found repeating it verbatim in the pages fetched.

## What are the separate Koin artifacts/modules for KMP projects, and how does a typical KMP project structure shared vs platform-specific DI code?

### Takeaway
Koin ships as a family of granular Gradle artifacts distributed via a `koin-bom` version catalog; `koin-core`, `koin-compose`, `koin-compose-viewmodel`, and `koin-core-viewmodel` are multiplatform (go in `commonMain`), while `koin-android` is Android/JVM-only (goes in `androidMain`). Typical KMP projects define shared bindings as Koin modules in `commonMain` and bridge platform differences using `expect`/`actual` classes injected into those same shared modules, rather than writing separate Koin module graphs per platform.

### Cited Findings
- Official KMP setup docs show this exact source-set split in `shared/build.gradle.kts`: `commonMain` gets `project.dependencies.platform(libs.koin.bom)` plus `libs.koin.core`, `libs.koin.compose`, `libs.koin.compose.viewmodel` (and `libs.koin.annotations` only if using the compiler plugin); `androidMain` gets `libs.koin.android`; `commonTest` gets `libs.koin.test`; the `iosMain` example shown adds no extra Koin dependency. — [Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)
- The docs list supported targets as Android, iOS (iosArm64, iosX64, iosSimulatorArm64), JVM (desktop/server), JS and Wasm (js, wasmJs), and macOS/Linux/Windows (Kotlin/Native) — confirming `koin-core` itself is the artifact that spans all of these; Compose-related artifacts (`koin-compose`, `koin-compose-viewmodel`) follow whatever targets Compose Multiplatform itself supports. — [Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)
- `koin-compose-viewmodel` on Maven Central (version 4.2.2 at time of search) depends on `koin-compose` and `koin-core-viewmodel`, and the Koin Compose reference docs describe it as the module providing `koinViewModel()` (and, on Android specifically, `koinActivityViewModel()`), marking it explicitly "Multiplatform" in the package table. — [Koin Compose reference docs](https://insert-koin.io/docs/reference/koin-compose/compose); [koin-compose-viewmodel on Maven Central](https://central.sonatype.com/artifact/io.insert-koin/koin-compose-viewmodel)
- `koin-android` is documented as the Android-specific dependency sitting alongside (not instead of) the Compose Multiplatform artifacts — i.e., it supplies Android platform bindings (e.g., `androidContext()`, Activity/Fragment scope helpers, WorkManager helpers) on top of the shared core. — [Compose Multiplatform ViewModel Injection with Koin DI & Ktor](https://proandroiddev.com/compose-multiplatform-viewmodel-support-with-koin-di-ktor-1f2c95acb446)
- `koin-ktor` appears in version-catalog examples as `io.insert-koin:koin-ktor`, tied to the shared Koin BOM version, used for integrating Koin into Ktor server applications (for backend/shared-server-code scenarios in KMP-adjacent projects); no official page describing its full API surface was retrieved in this research pass.
- In a worked KMP example, shared code declares a `platformModule` using `singleOf(::Platform)` where `Platform` is an `expect class` in `commonMain` with an `expect val name: String`; the iOS `actual` implementation reads `UIDevice` system name/version, and the Android `actual` implementation reads `android.os.Build.VERSION.SDK_INT`. The DI *module declaration* (`module { ... }`) stays entirely in common code — only the `actual` class implementation differs per platform, which is then bound into the common module via `singleOf`. — [Kotlin Multiplatform Setup walkthrough, Koin 4.0 docs](https://insert-koin.io/docs/4.0/reference/koin-mp/kmp)

### Inferences
- The structural pattern Koin encourages is: write Koin `module { }` DSL blocks in `commonMain` referencing `expect` types; implement the platform specifics as `actual` classes/functions in `androidMain`/`iosMain`; only add a *separate* per-platform Koin module when a dependency has no shared interface at all (e.g., Android-only `androidContext()`-dependent singletons, which must live in an Android-only module loaded only when `initKoin`/`startKoin` runs on Android, typically via `koin-android`'s `androidContext()` + `androidLogger()` extensions inside the Android app entry point rather than in `commonMain`).
- `koin-test` is multiplatform (declared in `commonTest`), meaning shared-module DI graphs can be verified (e.g. `checkModules()`) from common test code across all targets, which is a meaningful testing advantage over frameworks whose test tooling is JVM-only.

### Gaps
- No official page was found giving a complete, authoritative description of `koin-ktor`'s API (it's inferred only from a version-catalog reference); readers should check `insert-koin.io`'s Ktor integration page directly for specifics (not retrieved in this pass).
- Exact current version numbers for `koin-bom` conflict across sources (4.2.x cited in docs pages, 3.2.0 shown in an older walkthrough, 4.2.2 for `koin-compose-viewmodel` on Maven Central) — treat 4.2.x as the most recent confirmed line as of this research (Koin 4.2.0 was in RC/beta as late as the sources checked), and verify the exact patch version on Maven Central before publishing.

## How is Koin initialized from iOS (Swift) — the `initKoin()` pattern?

### Takeaway
The standard Koin KMP pattern is: define a parameterless (or default-parameter) `initKoin()` function in `commonMain` that calls `startKoin { modules(...) }`, wrap it with a truly parameterless `actual`/platform function in `iosMain` (since Swift cannot easily pass a Kotlin lambda/`KoinAppDeclaration`), and call that wrapper once from Swift at app launch — with Kotlin/Native's Objective-C export renaming rules producing a slightly different Swift call-site name (commonly prefixing `do` when the Kotlin function name starts with `init`).

### Cited Findings
- Official docs: in `commonMain`, `initKoin(config: KoinAppDeclaration? = null)` calls `startKoin`; in `iosMain` (file `KoinIos.kt`), `fun initKoinIos() = initKoin()` is declared as a parameterless wrapper "since Swift can't easily pass a Kotlin lambda." Swift then calls it as `KoinIosKt.doInitKoinIos()` from the `App` initializer — Kotlin/Native's Objective-C/Swift export adds a `do` prefix to functions whose Kotlin name starts with `init` (because Swift reserves the `init` prefix for initializers). — [Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)
- In the Koin 4.0-docs version of the same walkthrough, a shared helper calls `startKoin { modules(appModule()) }` where `appModule()` returns `listOf(commonModule, platformModule)`; the Swift `App` struct calls the generated wrapper once in its `init()`. The docs use the function name `initKoin`, but the Swift call-site shown is `HelperKt.doInitKoin()` — confirming the same `do`-prefix rename behavior across doc versions. — [Kotlin Multiplatform Setup, Koin 4.0 docs](https://insert-koin.io/docs/4.0/reference/koin-mp/kmp)
- Community guides follow the same shape with different names: one Medium guide names its bridge function `initKoin` in Kotlin and calls it from Swift as `KoinHelperKt.doInitKoin()`; another places the platform wrapper at `shared/src/iosMain/kotlin/di/KoinInitIos.kt` and calls `KoinInitIosKt.initKoinIos()` from Swift. The exact Swift symbol name always depends on the Kotlin file name + function name (Kotlin/Native's Objective-C header generation derives the Swift/ObjC symbol from `<FileName>Kt.<functionName>()`). — [proandroiddev.com: Building & Deploying a simple KMP app — Part 4: DI](https://proandroiddev.com/building-deploying-a-simple-kmp-app-part-4-dependency-injection-b7189b15e1ba)
- A ProAndroidDev article specifically about retrieving dependencies on iOS notes a related Kotlin/Native limitation: "there is no `KClass` object for Objective-C objects," so Swift/ObjC-native classes can't be referenced/injected directly by Koin's `KClass`-based resolution — the usual workaround is retrieving dependencies through a Swift/Kotlin bridge/helper function rather than injecting Swift types directly into the graph. — [How to "get()" your Koin dependency in iOS](https://proandroiddev.com/how-to-get-your-koin-dependency-in-ios-efb6d83ee165)

### Inferences
- The "wrap with a parameterless function" pattern exists specifically because Kotlin/Native's Objective-C/Swift interop cannot export generic/functional-type parameters (like `KoinAppDeclaration` lambdas) cleanly to Swift, so the common convention is: keep the flexible/configurable `initKoin(config: KoinAppDeclaration? = null)` signature in `commonMain` for use by other Kotlin code (e.g., tests, Android), but always expose a zero-argument `iosMain` wrapper as the only thing Swift actually calls.
- Developers should expect the literal Swift symbol name to differ from the Kotlin function name (the `do`-prefix insertion) and should verify the generated header/Swift API rather than assuming `KoinIosKt.initKoinIos()` will be callable verbatim — this is a common real-world gotcha worth flagging in an interview answer.

### Gaps
- No official source was found giving the precise, current (2025–2026) rule set for Kotlin/Native's Swift name-mangling of `init`-prefixed functions beyond the single documented example (`do` prefix); if asked for the general rule, note it's inferred from Koin's own docs example rather than from Kotlin/Native compiler documentation directly.

## How does Koin compare to KMP-ready alternatives for DI (manual DI, Kodein-DI, kotlin-inject, Metro) — is it the most widely adopted?

### Takeaway
Koin is widely described in community sources as the default/most common DI choice for new KMP projects in 2024–2025 (and was bundled into JetBrains' official Compose Multiplatform app template), but claims of being the single "most widely adopted" solution rest on vendor-supplied statistics (Kotzilla, Koin's commercial backer) rather than independent, verifiable comparison data; Kodein-DI remains a credible, more structured alternative for complex apps, and compile-time options (kotlin-inject via KSP, and the newer Metro compiler plugin) are gaining traction as reflection-free, compile-safe alternatives — notably, JetBrains' own KotlinConf sample app migrated from Koin to Metro.

### Cited Findings
- Koin's commercial maintainer Kotzilla states "9000+ GitHub Stars and 15M+ Monthly Downloads" for Koin (vendor-supplied figures). Independent GitHub star trackers show different snapshots: Ecosyste.ms lists 8,602 stars; a RepoMind snapshot shows 9,832; GitTrend shows "9.9k stars, 782 forks." — [kotzilla.io/koin](https://kotzilla.io/koin); [Ecosyste.ms Koin listing](https://awesome.ecosyste.ms/projects/github.com%2FInsertKoinIO%2Fkoin)
- A Koin blog post states Koin was added to "the official KMP App Template," described as "the official starting point for Compose Multiplatform," and that the template already uses Koin for DI — evidence of inclusion in a JetBrains-maintained sample, though the source is written by Koin's own team (self-reported, not an independent JetBrains statement). — [Koin in Kotlin Multiplatform: A Complete Guide](https://blog.insert-koin.io/koin-in-kotlin-multiplatform-a-complete-guide-576a24ffeeab)
- Counter-evidence: a Kotlin Slack community thread reports that JetBrains' own KotlinConf app (JetBrains/kotlinconf-app) merged a PR titled "Switch DI from Koin to Metro" (PR #581). Commenters in that same thread criticized the migration's framing, with one noting "the Metro code looks very alike to a Koin KSP implementation" and another arguing the original diff wasn't really exercising DI through Koin — these are community opinions, not official statements, but the PR's existence (migration away from Koin in a JetBrains-authored app) is a directly relevant, concrete counter-data-point to "JetBrains endorses Koin." — [Kotlin Slack: "dagger vs hilt vs koin vs metro..." thread](https://slack-chats.kotlinlang.org/t/33094191/dagger-vs-hilt-vs-koin-vs-metro-vs-lt-what-comes-next-gt-ser)
- On Koin vs. Kodein-DI: a June 2025 blog post comparing the two for KMP rates Kodein's documentation highly and its setup as simpler than "Koin's manual approach," and recommends Kodein for new KMP projects in that author's own comparison, while also noting Koin's lead developer has made strong multiplatform-compatibility claims dating back to 2021. A separate technical point raised: Kodein does not use a global/static context, so a Kodein container can be consumed directly, whereas "Koin requires a 'start' step" (i.e., `startKoin{}` creates implicit global state) — a structural/architectural difference relevant to testability. — [koin vs kodein for kmp di](https://livefasteattrashraccoon.github.io/2025/06/27/koin-vs-kodein-for-kmp-di.html)
- Other 2025 sources note kotlin-inject (KSP-based, compile-time) has "matured significantly" for multiplatform support, and that some teams prefer it specifically to avoid "Koin-style service-locator coupling" (i.e., Koin's classic DSL is a runtime service locator rather than true compile-time-verified constructor injection, unless the newer Koin Compiler Plugin is adopted). — [Kotlin Slack: DI framework recommendation thread](https://slack-chats.kotlinlang.org/t/18891180/i-m-looking-for-some-good-di-frameworks-for-kmp-with-mobile-)
- A 2025 DEV.to piece frames Koin as "the smart DI choice for 2025," and notes Koin 4.0 is built on Kotlin 2.0, with Compose Multiplatform APIs that are "identical between Koin Jetpack Compose and Koin Compose Multiplatform" (i.e., API parity between Android-only Jetpack Compose usage and cross-platform Compose Multiplatform usage is an explicit design goal). — [DEV.to: Modern Dependency Injection with Koin](https://dev.to/arsenikavalchuk/modern-dependency-injection-with-koin-the-smart-di-choice-for-2025-550i)

### Inferences
- "Koin is the most widely adopted DI for KMP" is a defensible but not rigorously proven claim as of this research pass: it has the strongest mindshare in tutorials/blog content and historical first-mover advantage in KMP-specific DI (multiplatform support since Koin 3.0.1), plus inclusion in community/official-adjacent starter templates, but independent, dated, apples-to-apples adoption data (vs. Kodein, kotlin-inject, Dagger/Hilt-for-Android-only, or Metro) was not found. An interview answer should present this as "widely considered the most popular/pragmatic choice, backed by template inclusion and ecosystem size," while flagging that rigorous market-share data doesn't exist and that momentum is shifting toward compiler-plugin-based (compile-safe) tools like Koin's own new plugin, kotlin-inject, and Metro.
- The Koin-to-Metro migration in JetBrains' KotlinConf app is the single most concrete "limitation" signal found: even a high-profile, JetBrains-adjacent KMP app moved away from Koin's runtime DSL toward a compile-time compiler-plugin approach, which should be mentioned as a nuance/caveat rather than omitted.

### Gaps
- No independent (non-vendor) download/star/usage comparison across Koin, Kodein-DI, kotlin-inject, and Metro was found; all adoption figures either come from Koin's own commercial backer (Kotzilla) or from informal community star-count snapshots that disagree with each other by over 1,000 stars depending on snapshot date.
- No official statement from JetBrains itself (blog, docs) was found explicitly recommending or endorsing Koin as the default DI for Compose Multiplatform; the available evidence is indirect (template inclusion, reported later migration away from it in one sample app).

## Concrete example: shared module definitions used across Android + iOS

### Takeaway
The canonical Koin KMP example is a `commonMain` Koin `module { }` block that binds an `expect class Platform` (implemented differently per target) plus shared business/view-model classes, loaded via a single `initKoin()` entry point called from each platform's native entry code (Android `Application.onCreate()`, iOS `App.init()`).

### Cited Findings
- From the Koin 4.0 KMP walkthrough: a `platformModule` in common code is declared as `module { singleOf(::Platform) }`, where `Platform` is declared `expect class Platform()` with `expect val name: String` in `commonMain`. The iOS `actual class Platform` implementation builds its `name` from `UIDevice.current.systemName` + `systemVersion`. The Android `actual class Platform` implementation builds its name from `"Android ${android.os.Build.VERSION.SDK_INT}"`. The shared `appModule()` function returns `listOf(commonModule, platformModule)`, which is passed to `startKoin { modules(appModule()) }` inside a shared `initKoin()`/helper function, called once from the Swift `App` struct's `init()`. — [Kotlin Multiplatform Setup, Koin 4.0 docs](https://insert-koin.io/docs/4.0/reference/koin-mp/kmp)
- From the current official KMP Setup doc (post-4.0): the Gradle structure is `shared/build.gradle.kts` with `kotlin("multiplatform")` plus `alias(libs.plugins.koin.compiler)` (when using annotations/compiler plugin), targeting `androidTarget`, `iosArm64`, `iosSimulatorArm64`, `jvm`; `commonMain` depends on the `koin-bom` platform plus `koin-core` (and optionally `koin-annotations`, `koin-compose`, `koin-compose-viewmodel`); `androidMain` adds `koin-android`; `commonTest` adds `koin-test`. The `initKoin(config: KoinAppDeclaration? = null)` function lives in `commonMain` and calls `startKoin`; `iosMain`'s `KoinIos.kt` adds the parameterless `initKoinIos()` wrapper that Swift calls as `KoinIosKt.doInitKoinIos()`. — [Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)

### Inferences
- The structural recipe an interview answer should be able to draw from memory: (1) one or more `module { }` blocks in `commonMain` referencing `expect` types and shared classes; (2) `expect`/`actual` classes/functions only for the pieces that genuinely differ per platform (device info, platform context, file system, etc.); (3) a single shared `initKoin()` composition function; (4) a thin, parameterless platform wrapper per target only where the host language can't call the common signature directly (iOS/Swift needs this; Android/Kotlin generally does not, since Android app code is also Kotlin and can call `initKoin()` directly, typically passing `androidContext(this)` via the `config` lambda inside `Application.onCreate()`).

### Gaps
- The research did not retrieve a single, complete end-to-end code sample combining Compose Multiplatform ViewModel injection (`koinViewModel()`) with the `expect`/`actual` `Platform` example in one project — the two were found in different doc versions/pages. A full worked sample should be assembled directly from `insert-koin.io`'s current KMP + Compose Multiplatform getting-started guides before being included verbatim in a report.

## Current (2025–2026) limitations or caveats for Koin on KMP

### Takeaway
As of the sources gathered, Koin's Wasm target support originated as an alpha-stage release (3.6.0-wasm-alpha2, dated 2023–2024) with no confirmed stable/non-alpha release note found in this research pass; separately, Koin's classic DSL is a runtime service-locator pattern (global `startKoin{}` state, resolution-by-`KClass` rather than compile-time-verified constructor injection) which has drawn criticism and is the stated motivation for Koin's own new Compiler Plugin as well as for some teams choosing kotlin-inject or Metro instead.

### Cited Findings
- Koin shipped a `3.6.0-wasm-alpha2` pre-release covering both `koin-core` and `koin-compose` for WebAssembly targets. — [Koin 3.6.0 wasm alpha2](https://blog.kotzilla.io/koin-3.6.0-wasm-alpha2)
- A GitHub issue tracked the Wasm work landing in the Koin 3.6 branch, with a later comment stating "4.0.0 will continue with wasm" — indicating Wasm support continued to evolve across the 3.6 → 4.0 transition rather than being finalized in one release. — [InsertKoinIO/koin issue #1634](https://github.com/InsertKoinIO/koin/issues/1634)
- Kotlin/Wasm itself reached Alpha status in December 2023 (introduced experimentally in Kotlin 1.8.20); as of Kotlin 1.9.20 the toolchain uses the WasmGC proposal, and Safari needed version 18.2+ for the Wasm GC features Kotlin/Wasm relies on (older Safari versions unsupported) — meaning any Koin-on-Wasm limitation is partly inherited from Kotlin/Wasm's own platform/browser-support maturity, not solely a Koin-specific gap. — [Kotlin for WebAssembly Goes Alpha, JetBrains blog](https://blog.jetbrains.com/kotlin/2023/12/kotlin-for-webassembly-goes-alpha/); [Kotlin Wasm configuration docs](https://kotlinlang.org/docs/wasm-configuration.html)
- No 2025-dated official Koin release note confirming a stable (non-alpha) Wasm release was found in this research pass — the most recent Wasm-specific evidence located is from the 2023–2024 alpha cycle.
- On runtime service-locator concerns: a June 2025 Koin-vs-Kodein comparison notes Koin's global `startKoin{}` creates implicit shared state, contrasted with Kodein's non-global container that "can be consumed directly" — raised as a testability/architecture caveat. — [koin vs kodein for kmp di](https://livefasteattrashraccoon.github.io/2025/06/27/koin-vs-kodein-for-kmp-di.html)
- On Kotlin/Native concurrency: the only reference found was the Koin 4.0-era KMP doc mentioning a "New Native Memory Management" section instructing users to enable an experimental Gradle property in `gradle.properties` — but no further detail on what specifically changes for Koin singletons under the new Kotlin/Native memory model was retrieved from that page. — [Kotlin Multiplatform Setup, Koin 4.0 docs](https://insert-koin.io/docs/4.0/reference/koin-mp/kmp)
- The Koin Compiler Plugin (K2-based, requiring Kotlin 2.3.x+ and Koin 4.2.0-RC2+) was introduced specifically to validate the dependency graph at compile time and catch missing/misconfigured bindings before runtime — implicitly acknowledging that the classic DSL-only approach's main weakness is deferred (runtime-only) error detection. — [koin-compiler-plugin release 0.4.0](https://github.com/InsertKoinIO/koin-compiler-plugin/releases/tag/0.4.0)
- Kotlin/Native interop caveat: Koin's `KClass`-based resolution cannot reference Objective-C/Swift-native classes directly ("there is no `KClass` object for Objective-C objects"), so Swift types can't be injected directly into a Koin graph — developers work around this via Kotlin-side bridge/helper functions exposed to Swift. — [How to "get()" your Koin dependency in iOS](https://proandroiddev.com/how-to-get-your-koin-dependency-in-ios-efb6d83ee165)

### Inferences
- For an interview answer on "current limitations," the most defensible, source-backed points are: (1) Wasm support's maturity timeline is genuinely unclear past the 2023–2024 alpha stage based on available sources — this should be flagged as needing a live check of Koin's GitHub releases page rather than asserted as "stable" or "unstable" with confidence; (2) the classic Koin DSL remains a runtime-resolved service locator with global mutable state (`startKoin{}`), which is the real architectural trade-off versus compile-time DI tools, and Koin's own 4.2 Compiler Plugin is a direct response to this; (3) Kotlin/Native ObjC interop means Swift-native types cannot be bound directly — DI across the Swift boundary always goes through a thin Kotlin bridge, not a limitation unique to Koin but one that shows up specifically when wiring Koin to a SwiftUI-driven iOS app.

### Gaps
- Could not confirm the current (as of November 2026) stability status of Koin's Wasm target (`wasmJs`) — whether it has graduated out of alpha into a stable, production-recommended state — since no 2025–2026-dated Koin release notes were surfaced by search. This should be verified directly against Koin's GitHub Releases page or insert-koin.io changelog before stating a definitive maturity level in the final report.
- Could not find specific, documented guidance from Koin's own docs on Kotlin/Native strict vs. new memory model implications for singleton (`single { }`) thread-safety/freezing — only a passing mention of an experimental Gradle flag, with no explanation of what breaks or changes. This is a gap that should ideally be filled by checking Koin's current Kotlin/Native-specific documentation page directly, which was not located as a distinct page in this research pass.
- Exact current stable Koin version (4.2.0 final vs. still in RC/beta at time of writing, or a possible 4.3/5.0) could not be pinned down precisely — sources found were pre-release (beta/RC) notes; verify on Maven Central / insert-koin.io before publishing a specific version number in the final report.
