# Koin trades compile-time safety for Kotlin-native flexibility

Koin is best understood not as "Dagger but simpler" but as a **runtime container with a service-locator core wrapped in a constructor-injection-friendly DSL**: `module { }` blocks register plain Kotlin lambdas describing how to build a type, and `get()`/`by inject()` look that registration up by type (plus an optional qualifier) at the moment it's needed, rather than Dagger/Hilt's approach of generating direct factory calls at compile time ([insert-koin.io, Koin vs Hilt](https://insert-koin.io/docs/intro/koin-vs-hilt)). This single architectural choice explains nearly everything else about Koin: why it needs no annotation processor for its classic DSL, why it is the dominant pragmatic choice for Kotlin Multiplatform (KMP) sharing DI logic across Android and iOS, why it defers most error detection to runtime unless you opt into `verify()` or the newer Koin Compiler Plugin, and why its "no reflection" marketing claim is disputed rather than settled. Koin's own documentation is unusually candid about the trade-off: Hilt gets full build-time graph verification, zero runtime lookup cost, and Google's official backing, while Koin gets less boilerplate, true cross-platform portability, and the ability to load or unload modules at runtime — something a compiled Hilt graph simply cannot do ([insert-koin.io, Koin vs Hilt](https://insert-koin.io/docs/intro/koin-vs-hilt)). The project has also been visibly converging toward Dagger-style safety over the past two years, shipping Koin Annotations, then a deprecated KSP processor, and now a K2 Compiler Plugin that adds compile-time graph validation — without changing the underlying runtime-resolution execution model. For interview purposes, the most defensible framing is: Koin is a pragmatic, Kotlin-native DI container that resolves dynamically by default and now offers opt-in, still-maturing compile-time safety, while Dagger/Hilt resolve statically by default and offer no equivalent opt-out into Koin's runtime flexibility.

## The "pragmatic, no-reflection" pitch is real but narrower than it sounds

Koin describes itself as "a pragmatic lightweight dependency injection framework for Kotlin developers... a DSL, a light container and a pragmatic API" ([Koin docs/mirrors](https://awesome.ecosyste.ms/projects/github.com%2Finsertkoinio%2Fkoin-getting-started)), and an older, widely repeated framing claims it is "written in pure Kotlin, using functional resolution only: no proxy, no code generation, no reflection" ([Koin mirror text](https://en.paradigmadigital.com/dev/dependency-injection-with-koin/); [Medium retrospective](https://medium.com/the-kotlin-chronicle/advocating-for-and-against-koin-2281869e892b)). The stated rationale, per third-party technical writing, is that reflection and code generation hurt performance on resource-constrained mobile devices and lengthen build times — the two costs Koin's classic DSL was designed to avoid ([Paradigma Digital](https://en.paradigmadigital.com/dev/dependency-injection-with-koin/)). This claim deserves scrutiny rather than repetition: a November 2025 droidcon/ProAndroidDev piece pushes back directly, arguing Koin still builds its dependency graph **at runtime** and uses Kotlin's reflection-adjacent machinery to infer constructor parameters, and that "no code generation" is accurate for the classic path but "no reflection" is a looser claim than it appears ([droidcon, "Hilt vs Koin: The Hidden Cost of Runtime Injection"](https://www.droidcon.com/2025/11/26/hilt-vs-koin-the-hidden-cost-of-runtime-injection-and-why-compile-time-di-wins/)). The more precise technical resolution is that Koin's classic lambda DSL (`single { MyClass(get()) }`) never calls `Class.forName` or builds a dynamic proxy — Java-style runtime reflection — but it does lean on Kotlin's `inline`/`reified` generic functions to resolve types, and Koin's own docs describe the constructor-reference forms (`singleOf`, `factoryOf`) as "reflection-free dependency injection," which only makes sense as a contrast if the classic lambda form is being treated as *not* fully reflection-free either ([Koin 4.1.0 docs mirror, "constructor-reference"](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/constructor-reference.md)). An interview answer should treat "Koin uses no reflection" as a disputed marketing simplification, not a settled fact, and should distinguish three generations of the framework: the classic runtime DSL (pure Kotlin, no codegen, debatable reflection claim), **Koin Annotations** (KSP-based, now deprecated in its original processor form), and the current **Koin Compiler Plugin** (a K2 compiler plugin that generates constructor wiring and performs build-time graph checks, described by Koin's docs as letting annotations and the Verify API run as "first-class citizens, equally powerful" — explicitly narrowing, not eliminating, the compile-time gap with Hilt) ([insert-koin.io, Koin vs Hilt](https://insert-koin.io/docs/intro/koin-vs-hilt)).

## Runtime internals: a registry of lazy factories behind `get()` and `inject()`

Calling `startKoin { modules(appModule) }` constructs a `KoinApplication` (the container's configuration object) and registers it in `GlobalContext`, a process-wide holder of exactly one live `Koin` instance; `startKoin` can only run once per process, and a second call throws `KoinApplicationAlreadyStartedException` — later modules must go through `loadKoinModules()` instead ([insert-koin.io, "Starting Koin"](https://insert-koin.io/docs/reference/koin-core/starting-koin); [DSL reference](https://insert-koin.io/docs/reference/koin-core/dsl)). `koinApplication { }` (lowercase) is the escape hatch: it builds a standalone `KoinApplication` that is never registered in `GlobalContext`, so global APIs like `KoinComponent`, `by viewModel()`, and `koinInject()` cannot see it — this is the documented pattern for SDKs, libraries, and isolated/parallel tests that must not pollute or be polluted by a host app's container ([Starting Koin reference](https://insert-koin.io/docs/reference/koin-core/starting-koin)). `KoinComponent` is the marker interface that exposes `get()`, `by inject()`, `getProperty()`, and `getKoin()` to any class Koin doesn't construct for you; `get()` resolves eagerly at the call site, while `by inject()` is a lazy property delegate — effectively `lazy { get<T>() }` — deferring resolution to first property access, with a `LazyThreadSafetyMode` defaulting to `SYNCHRONIZED` on the JVM ([insert-koin.io, "Koin Component"](https://insert-koin.io/docs/reference/koin-core/koin-component); [Retrieving Dependencies reference](https://insert-koin.io/docs/reference/koin-core/injection)).

Internally, each `single`/`factory`/`scoped` definition is wrapped in an `InstanceFactory` subtype — `SingleInstanceFactory` caches and returns one instance, `FactoryInstanceFactory` builds fresh on every call, and `ScopedInstanceFactory` builds once per open scope instance — looked up by a registry key combining the requested type and optional qualifier. This internal class structure is corroborated by real bug reports (a concurrency issue referencing `SingleInstanceFactory.create()`/`get()` in `InsertKoinIO/koin` PR #914) and by a reported "InstanceRegistry already contains index 'Factory'" collision error, but the research notes flag that the exact current field/method names could not be independently confirmed against today's Kotlin source in this pass — direct GitHub fetches returned 404s — so these internals should be presented as the best available approximation, version-unpinned, rather than quoted as verified source code ([kotlinlang Slack thread](https://slack-chats.kotlinlang.org/t/499782/hi-there-i-think-i-just-found-a-concurrency-issue-in-koin-af); [kotlinlang Slack thread on index collision](https://slack-chats.kotlinlang.org/t/499823/when-binding-two-singletons-like-this-single-someclass-facto)). Instantiation is **lazy by default**: a `single { }` is built on its first `get()`/`inject()` call, not at `startKoin` time, unless marked `createdAtStart = true` (or the whole module is declared `module(createdAtStart = true) { }`), in which case `createEagerInstances()` builds it immediately when Koin starts; real-world reports note that modules added later via `loadKoinModules()` do not automatically get their eager instances created, a quirk that remained unresolved as bug-vs-intended-behavior in community discussion ([Koin docs mirror, "application"](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core/4.1.0/files/docs/application.md); [GitHub issue #1318](https://github-redirect.dependabot.com/InsertKoinIO/koin/issues/1318)).

Circular dependencies deserve particular care in an interview because the real story is more nuanced than "Koin detects cycles." A Koin maintainer stated on Kotlin Slack that a cycle-detector **did exist in Koin 2.1.x but was deliberately removed for performance reasons**, adding it "may be worth reconsidering later" ([kotlinlang Slack thread](https://slack-chats.kotlinlang.org/t/499636/hello-i-m-having-this-stacktracke-while-i-m-trying-to-work-w)). Without that detector, a true A→B→A cycle in the classic runtime DSL most plausibly surfaces as a `StackOverflowError` from infinite mutual recursion inside `get()`/`create()`, though Koin's troubleshooting docs also describe a generic "Circular dependency detected" runtime message, and the research could not pin down definitively whether that message comes from an explicit resolution-stack guard or is just a loose description of the stack overflow — flag this as unresolved rather than stating a single mechanism with confidence ([insert-koin.io troubleshooting docs](https://insert-koin.io/docs/reference/koin-core/troubleshooting)). Only two Koin tools catch cycles deterministically today: the **Koin Compiler Plugin**, which fails the build with an error such as `[Koin][KOIN-D004] Circular dependency detected:`, and `verify()`, whose test-time failure throws `CircularInjectionException` with a message like "Circular injection between ... Fix your Koin configuration!" ([Koin troubleshooting docs](https://insert-koin.io/docs/reference/koin-core/troubleshooting); [Koin verify() docs](https://insert-koin.io/docs/reference/koin-test/verify)). The standard fix in all cases is a design fix, not a framework trick: inject one side of the cycle as `Lazy<T>` and avoid reading `.value` inside `init`, or — the more durable solution — extract the shared responsibility into a third class both original classes depend on.

Missing-binding exceptions are another area where terminology has drifted and should be stated carefully. The single most reliable, well-documented current exception for an unresolved dependency is `NoDefinitionFoundException`, with a message format like `"No definition found for type 'com.example.UserRepository' on scope '['_root_']'."` — common causes are an unloaded module, a qualifier mismatch, a request for an interface that was never explicitly bound, or a scoped definition requested from the wrong scope ([Koin troubleshooting docs](https://insert-koin.io/docs/reference/koin-core/troubleshooting)). The frequently-searched term `NoBeanDefFoundException` shows up across many historical Stack Overflow and Slack threads spanning Koin 0.9.x onward and may be either a genuinely older exception name that was later renamed, or community conflation with Spring's `NoSuchBeanDefinitionException` — the research notes could not confirm with certainty whether `NoBeanDefFoundException` is Koin's true historical name or a misattribution, so an interview answer should mention both terms but commit to `NoDefinitionFoundException` as the name to cite as current ([Kotlin Slack thread](https://slack-chats.kotlinlang.org/t/13842190/hi-i-cannot-update-my-project-from-koin-0-9-1-to-0-9-2-due-t); [Stack Overflow via Kiwix mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/51195471/koin-android-org-koin-error-nobeandeffoundexception)). A second common failure, `InstanceCreationException`, wraps a found-but-failed construction — the real cause is almost always in the nested `Caused by:` entry, a detail junior developers frequently miss — and a family of scope-lifecycle exceptions (`ClosedScopeException`, `ScopeNotCreatedException`, `ScopeAlreadyCreatedException`, `MissingScopeValueException`) covers requests made against scopes that are closed, never created, duplicated, or missing a `declare()`d value ([Koin troubleshooting docs](https://insert-koin.io/docs/reference/koin-core/troubleshooting)).

## The DSL: five definition kinds, scopes, qualifiers, and two generations of error-catching

Koin's DSL organizes definitions inside `module { }` blocks, which are composed via `includes(...)` or the `+` operator and registered either eagerly through `startKoin { modules(...) }` or lazily (loaded on a background coroutine, Koin 4.2+ loading each in parallel) through `lazyModule { }` plus `lazyModules(...)`, with `koin.waitAllStartJobs()` available to await them ([DSL reference](https://insert-koin.io/docs/reference/koin-core/dsl); [Koin 4.2.0 release notes](https://newreleases.io/project/github/InsertKoinIO/koin/release/4.2.0)). Koin's definitions reference page names five kinds: `single` (one instance for the container's lifetime — Repositories, database clients), `factory` (a brand-new instance on every resolution — stateless use cases/interactors), `scoped` (one instance per open scope *instance*, shared while that scope is open and discarded on close — per-session or per-screen state), `viewModel`, and `worker` ([Definitions reference](https://insert-koin.io/docs/reference/koin-core/definitions/)). Each has a classic lambda form (`single { Database() }`) and a Constructor DSL form that autowires parameters purely by type (`singleOf(::Database)`); the Constructor DSL cannot carry qualifiers, so a qualified dependency forces a drop back to the explicit lambda form ([Qualifiers reference](https://insert-koin.io/docs/reference/koin-core/qualifiers)). `scoped` is structurally distinct because it must live inside a `scope<T> { }` or `scope(named(...)) { }` block rather than loose at module top level, and a `factory` declared inside a scope block is still a fresh instance on every call but may depend on that scope's `scoped` instances ([Scopes reference](https://insert-koin.io/docs/reference/koin-core/scopes)).

Binding a concrete type to an interface uses `bind<Interface>()`/`binds(listOf(...))` as an *additional* resolvable type on top of the concrete class, versus declaring the interface as the generic return type directly (`single<UserRepository> { UserRepositoryImpl(get()) }`), which makes the interface the *only* resolvable type for that definition — a subtlety that matters because `get<UserRepositoryImpl>()` will fail in the latter case but succeed in the former ([DSL reference](https://insert-koin.io/docs/reference/koin-core/dsl); [Definitions reference](https://insert-koin.io/docs/reference/koin-core/definitions/)). Disambiguating multiple bindings of the same type uses qualifiers — string (`named("local")`), type (`named<LocalDb>()`, aliased `qualifier<LocalDb>()`), or enum (`named(DbType.LOCAL)`) — and the research flags a genuine gotcha: enum qualifiers are not a separate qualifier type at all, they're string qualifiers generated from the lowercased enum entry name, so `named(DbType.LOCAL)` and `named("local")` silently collide if mixed ([Qualifiers reference](https://insert-koin.io/docs/reference/koin-core/qualifiers)). Runtime values are threaded into definitions via `parametersOf(...)` (matched position-first-then-type by default; `parameterArrayOf` is position-only, `parameterSetOf` is type-only), intended for `factory`/`scoped` definitions since a `single` only consumes the parameters passed on its first creation and silently ignores later ones ([Injected parameters reference](https://insert-koin.io/docs/reference/koin-core/injection-parameters)).

Scopes are Koin's mechanism for lifecycles between "whole container" and "fresh every time." A `Scope` object is created via `Koin.createScope(scopeId, qualifier, source)` / `getOrCreateScope` / `getScope`, resolved from with `scope.get()`, linked to other scopes with `linkTo()`/`unlink()` so resolution can fall through (current scope → linked scopes in order → root scope last, and the root scope cannot itself be linked), and must be explicitly ended with `scope.close()` or `Koin.deleteScope(scopeId)` to release cached instances — a scope that is never closed behaves like a leak, because its registry entry (and anything it transitively holds, including a captured Activity or View) stays reachable ([Koin docs mirror, "scope-management" 4.1.0](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-core-jvm/4.1.0/files/docs/scope-management.md); [Koin Android Best Practices](https://insert-koin.io/docs/reference/koin-android/best-practices)). On Android, Koin ships pre-built scope archetypes — `activityScope`/`ScopeActivity`, `activityRetainedScope` (survives configuration changes, stored against a ViewModel), `fragmentScope` (links to its host Activity's scope by default; closes on `ON_DESTROY`, not `onDestroyView()`, so Views must be released separately), and `viewModelScope`/`ScopeViewModel` — that auto-close on the relevant lifecycle callback, in contrast to a scope created manually via `getKoin().createScope()`, which has no lifecycle hook and must be closed by hand ([Koin Android Scope docs](https://insert-koin.io/docs/4.1/reference/koin-android/scope)). The research also surfaced an unresolved documentation conflict worth flagging rather than glossing over: Compose's `KoinScope` composable is explicitly documented on the official page as requiring the developer to close the scope manually, while a third-party mirror labeled Koin 4.1.0 describes an auto-closing variant — the official page should be treated as authoritative until a specific version is confirmed to change this ([Scopes in Compose (official)](https://insert-koin.io/docs/reference/koin-compose/compose-scopes) vs. [Tessl mirror, v4.1.0](https://tessl.io/registry/tessl/maven-io-insert-koin--koin-compose-jvm/4.1.0/files/docs/scope-management.md)).

Catching problems before they hit production has gone through a documented, two-generation evolution. `checkModules()` is the older mechanism: it runs inside `koinApplication { modules(...); checkModules() }` and actually launches a sandboxed instantiation pass over every definition, requiring real or supplied values (`withInstance()`, `withParameter(s)`) for anything it can't build on its own — it is now **deprecated since Koin 4.0** in favor of `verify()` ([Koin checkModules() docs synthesis](https://lts.insert-koin.io/docs/reference/koin-test/checkmodules); [Kotlin Slack thread](https://slack-chats.kotlinlang.org/t/13841383/could-you-run-a-test-that-checks-your-modules-for-you-test-f)). `verify()` (added in Koin 3.3, extended with `injections`/`injectedParameters()` in 4.0) is a lighter, JVM-only, static check: it reads each definition's constructor and confirms every parameter type has a matching definition, without instantiating anything, and throws `MissingKoinDefinitionException` for a gap; `extraTypes` whitelists externally-injected types like `SavedStateHandle`, and `androidVerify()` (from `koin-android-test`) adds common Android types automatically ([insert-koin.io, "Verify"](https://insert-koin.io/docs/4.0/reference/koin-test/verify)). Its documented limitation is real and worth stating plainly in an interview: `verify()` checks constructors only, so it is blind to qualifier mismatches, property injection, or `get()` calls made inside a lambda body, and community reports describe genuinely broken bindings that `verify()` failed to catch ([Kotlin Slack thread](https://slack-chats.kotlinlang.org/t/13841383/could-you-run-a-test-that-checks-your-modules-for-you-test-f?t=v2)). The newest layer, the **Koin Compiler Plugin**, performs real build-time graph validation — enabled by default via `compileSafety = true` — and Koin's own blog positions it as a replacement for both `checkModules()` and `verify()` "in most cases," though a 1.1.0 release note removed per-module validation and the plugin skips compilations with no Koin entry point, meaning runtime-loaded modules, library-only modules, and dynamically-assembled module lists (flagged `KOIN-W003`) still fall outside its coverage and still need `verify()` ([insert-koin.io, "Compile-Time Safety"](https://insert-koin.io/docs/reference/koin-compiler/compile-safety); [Koin blog: Compiler Plugin 1.0.0-RC1](https://blog.insert-koin.io/unlocking-koin-compile-safety-6278840ab171)). Finally, the original KSP-based annotation processor, `koin-ksp-compiler`, **is itself deprecated and slated for removal** — the annotations it processed (`@Single`/`@Singleton`, `@Factory`, `@Scoped`, `@Module`, `@ComponentScan`, etc.) are not deprecated and remain fully supported, just now processed by the K2 Compiler Plugin instead of KSP ([KSP Processor Setup (Deprecated)](https://insert-koin.io/docs/setup/annotations-ksp); [Koin Compiler Plugin intro](https://insert-koin.io/docs/intro/koin-compiler-plugin)).

## Kotlin Multiplatform is Koin's clearest, least-disputed advantage

`koin-core` is pure Kotlin with no JVM-reflection or Android-API dependency, which is why identical `module { }` code compiles and runs unmodified on every Kotlin compilation target — JVM, Android, Kotlin/Native (iOS, macOS, Linux, Windows), and Kotlin/JS and Wasm ([Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)). This was not true from Koin's inception — multiplatform compatibility for the core package was specifically announced in the Koin 3.0.1 release, making KMP support a deliberate later addition rather than an original design pillar ([Koin 3.0.1 Release blog](https://blog.insert-koin.io/koin-3-0-1-release-2-x-redeploy-856c2cc6edec)). A typical KMP project distributes Koin artifacts via a `koin-bom` version catalog: `koin-core`, `koin-compose`, `koin-compose-viewmodel`, and `koin-core-viewmodel` go in `commonMain` (and `koin-test` in `commonTest`), while `koin-android` is Android/JVM-only and goes in `androidMain` ([Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)). The idiomatic pattern is to write the actual `module { }` DSL entirely in `commonMain`, referencing `expect` classes for anything that genuinely differs per platform (device name, file system, platform context), and bind the platform-specific `actual` implementation into the shared module via `singleOf(::Platform)` — only truly platform-only dependencies (like Android's `androidContext()`-dependent singletons) get a separate, platform-scoped module ([Kotlin Multiplatform Setup, Koin 4.0 docs](https://insert-koin.io/docs/4.0/reference/koin-mp/kmp)).

Initializing Koin from Swift surfaces a real, commonly-hit interop gotcha: Swift cannot cleanly call a Kotlin function that takes a lambda parameter (such as `initKoin(config: KoinAppDeclaration? = null)`), so the convention is a parameterless wrapper in `iosMain` — e.g. `fun initKoinIos() = initKoin()` — which Kotlin/Native's Objective-C export then renames on the Swift side, commonly inserting a `do` prefix because Swift reserves the bare `init` prefix for initializers (so the Swift call site becomes something like `KoinIosKt.doInitKoinIos()`) ([Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)). A related, often-overlooked Kotlin/Native limitation is that **there is no `KClass` object for Objective-C/Swift-native classes**, so Swift-native types cannot be injected directly into a Koin graph — DI across that boundary always goes through a thin Kotlin-side bridge function, not a Koin-specific deficiency so much as a Kotlin/Native interop constraint that happens to matter wherever Koin's `KClass`-keyed resolution meets Swift ([ProAndroidDev: "How to get() your Koin dependency in iOS"](https://proandroiddev.com/how-to-get-your-koin-dependency-in-ios-efb6d83ee165)).

Two things should be stated as genuinely uncertain rather than confidently asserted. First, **Koin's Wasm (`wasmJs`) target maturity is unclear past its 2023–2024 alpha release** (`3.6.0-wasm-alpha2`); no 2025–2026-dated Koin release note confirming a stable, non-alpha Wasm release was located in this research, and Kotlin/Wasm itself only reached Alpha in December 2023 with browser-support caveats (older Safari versions lack the required WasmGC features) — so any claim that Koin-on-Wasm is "production-ready" should be checked against Koin's current GitHub releases before repeating it ([Koin 3.6.0 wasm alpha2](https://blog.kotzilla.io/koin-3.6.0-wasm-alpha2); [Kotlin for WebAssembly Goes Alpha](https://blog.jetbrains.com/kotlin/2023/12/kotlin-for-webassembly-goes-alpha/)). Second, **the exact current stable Koin version number is not pinned down with confidence** — sources found during this research describe a 4.2.0/4.2.1 line still cycling through RC/beta/patch releases (4.2.1 patched a `runOnKoinStarted` binary-compatibility regression and added "Compile Safety with Koin Compiler 1.0.0-RC1"), and the Compiler Plugin itself was still iterating (0.4.0 → 1.1.0 → 1.2.1) across the sources gathered, so cite "Koin 4.2.x as of late 2025/early 2026" rather than a single precise version ([Koin 4.2.0 release notes](https://newreleases.io/project/github/InsertKoinIO/koin/release/4.2.0)). On adoption, Koin is widely treated as the default pragmatic DI choice for new KMP projects and was bundled into JetBrains' official Compose Multiplatform app template ([Koin blog: "Koin in Kotlin Multiplatform"](https://blog.insert-koin.io/koin-in-kotlin-multiplatform-a-complete-guide-576a24ffeeab)) — but this should not be overstated: JetBrains' own `kotlinconf-app` sample later merged a PR titled "Switch DI from Koin to Metro," a concrete, if debated, counter-signal that even a high-profile JetBrains-adjacent app moved toward a compile-time compiler-plugin alternative ([Kotlin Slack: "dagger vs hilt vs koin vs metro" thread](https://slack-chats.kotlinlang.org/t/33094191/dagger-vs-hilt-vs-koin-vs-metro-vs-lt-what-comes-next-gt-ser)). Vendor-reported adoption numbers (Koin's commercial backer Kotzilla cites "9000+ GitHub Stars and 15M+ Monthly Downloads") should be read as promotional rather than independently audited, since third-party star trackers disagree with each other by over a thousand stars depending on snapshot date ([kotzilla.io/koin](https://kotzilla.io/koin); [Ecosyste.ms Koin listing](https://awesome.ecosyste.ms/projects/github.com%2FInsertKoinIO%2Fkoin)).

## Koin vs Dagger vs Hilt: the honest, balanced comparison

The structural split is unambiguous and is the single fact from which almost every other comparison point follows: Dagger's annotation processor (kapt or KSP) statically analyzes `@Component`/`@Module`/`@Inject`/`@Provides` annotations and generates a `Dagger<Component>Impl` plus a `Factory`/`Provider`-implementing class per binding, so the app calls generated factories directly at runtime with **no lookup cost**; Koin keeps the graph in a runtime container and resolves by type (plus qualifier) on every `get()` call ([Dagger GitHub README](https://github.com/google/Dagger); [insert-koin.io, Koin vs Hilt](https://insert-koin.io/docs/intro/koin-vs-hilt)). Hilt sits on top of Dagger specifically for Android: `@HiltAndroidApp` generates an application-level container, `@AndroidEntryPoint` generates a per-class Hilt component enabling field injection in Activities/Fragments/Services, `@HiltViewModel` integrates with the ViewModel architecture component, and every Hilt module must declare `@InstallIn(SingletonComponent::class)` or another fixed generated component to say where it lives — a predefined hierarchy that removes the need to hand-write `@Component`/`@Subcomponent` interfaces the way raw Dagger requires ([developer.android.com, summarized via search](https://developer.android.com/training/dependency-injection/hilt-jetpack)).

| Dimension | Dagger / Hilt | Koin |
|---|---|---|
| Graph resolution | Compile-time codegen; generated factories called directly, no runtime lookup ([Dagger GitHub](https://github.com/google/Dagger)) | Runtime container; `get()` looks up by type+qualifier on every call ([insert-koin.io](https://insert-koin.io/docs/intro/koin-vs-hilt)) |
| Missing/ambiguous bindings | Always caught at compile time; build fails ([insert-koin.io](https://insert-koin.io/docs/intro/koin-vs-hilt)) | Runtime `NoDefinitionFoundException` by default; `verify()`/Compiler Plugin needed to shift this earlier ([insert-koin.io, Verify](https://insert-koin.io/docs/4.0/reference/koin-test/verify)) |
| Cycle detection | Compile-time, unconditional | Historically removed at runtime (2.1.x detector dropped); only the Compiler Plugin and `verify()` catch it deterministically today ([Kotlin Slack](https://slack-chats.kotlinlang.org/t/499636/hello-i-m-having-this-stacktracke-while-i-m-trying-to-work-w)) |
| Build-time cost | Annotation-processing pass (kapt/KSP) adds measurable time, project-dependent ([search synthesis](https://dev.to/mikkelofficial7/koin-vs-dagger-2-vs-hilt-which-one-should-we-use-1e0n)) | No processor needed for the classic DSL; Compiler Plugin adds a cost only if adopted |
| Runtime overhead | Near-zero added DI cost beyond ordinary construction (theoretical, undisputed) | Real but small per-resolution lookup cost + startup registration ([insert-koin.io](https://insert-koin.io/docs/intro/koin-vs-hilt)) — **magnitude is genuinely disputed across sources, see below** |
| KMP / iOS support | Not possible — kapt/KSP as used by Dagger has no Kotlin/Native code-generation path; Hilt is explicitly Android-only ([CommonsWare community](https://commonsware.com/community/t/replacing-koin-with-dagger/423)) | Native support across JVM, Android, Kotlin/Native (iOS/macOS/Linux/Windows), JS, and Wasm (alpha) ([Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)) |
| Runtime flexibility | Fixed once compiled — no post-build module loading/unloading | `loadKoinModules()`/`lazyModule {}` allow runtime loading and unloading, useful for feature flags/plugin architectures ([insert-koin.io](https://insert-koin.io/docs/intro/koin-vs-hilt)) |
| Boilerplate | Hilt reduces raw Dagger's component ceremony but still needs `@Inject`, `@Binds`/`@Provides`, `@InstallIn`, `@HiltAndroidApp` | Classic DSL needs none of that; `single { Foo(get()) }` or `singleOf(::Foo)` suffices |
| Official backing | Google-maintained, officially recommended for Android | Community/Kotzilla-maintained, not Google-endorsed |

The performance question is the one area where this research found genuine, unresolved disagreement rather than a clean answer, and it should be presented that way rather than picked for the reader. Koin's own docs concede the directional point — Hilt has "no runtime lookup," Koin "costs a lookup per resolution plus registration work at startup" — but sources disagree sharply on magnitude: one 2024 benchmark against Google's "Now in Android" sample app (Koin 4.0.1-Beta1 vs. Hilt 2.52) reportedly found near-parity, while a separate community comparison claims Koin is measurably slower "especially in large-scale applications" ([insert-koin.io, Koin vs Hilt](https://insert-koin.io/docs/intro/koin-vs-hilt); [DEV Community comparison](https://dev.to/mikkelofficial7/koin-vs-dagger-2-vs-hilt-which-one-should-we-use-1e0n)). Neither benchmark article could be independently fetched in full during this research (both returned HTTP 403), so treat any specific millisecond figure attributed to them as secondhand and unverified rather than citable fact. Build-time comparisons have the same shape: kapt's stub-generation step is a documented major cost (one analysis attributed 75.8% of a project's relevant build time to it), KSP is generally faster than kapt but not universally so (a tracked Dagger GitHub issue is literally titled "[KSP] Performance regression vs KAPT"), and no apples-to-apples Koin-vs-Hilt-on-KSP build-time benchmark was found at all — so the safest interview framing is "Dagger/Hilt's annotation-processing pass adds real, project-size-dependent build time; Koin's classic DSL adds effectively none; the gap has narrowed since Dagger/Hilt adopted KSP, but hard comparative numbers are thin."

The most philosophically loaded interview question in this space — **"is Koin even really dependency injection, or a service locator?"** — has a defensible, nuanced answer rather than a yes/no. Structurally, Koin's container mechanism is a service locator: `get()`/`by inject()` pull from a registry by type at the call site, which several practitioners point to directly, with one widely-echoed framing stating flatly that "only Dagger uses a dependency injection (DI) pattern; Koin and Kodein are service locators" ([Medium comparison, via search synthesis](https://medium.com/@lukmagayoarizky/battle-between-dagger-and-koin-in-android-development-9988893ca6c)). But the critique is sharpest against *usage*, not just mechanism: Koin's own idiomatic style confines container calls to module definition lambdas (`single { Foo(get(), get()) }`), which keeps `Foo` itself free of any Koin import and fully testable with plain constructor calls — the "service locator smell" really shows up only when teams instead scatter `by inject()`/`get()` as properties through business-logic classes. It's also worth noting, as a counterpoint that defuses a false binary, that Hilt itself has locator-style seams at Android integration boundaries — `hiltViewModel()` in a composable is structurally similar to Koin's `koinViewModel()` — meaning the service-locator line is really about *how much* of an app's code touches the container directly, not a clean Koin-vs-Dagger split ([Kotlin Slack thread](https://slack-chats.kotlinlang.org/t/33094191/dagger-vs-hilt-vs-koin-vs-metro-vs-lt-what-comes-next-gt-ser)).

## Interview Q&A: the questions most likely to come up, answered precisely

**Q: What is the fundamental architectural difference between Dagger/Hilt and Koin?**
A: Dagger/Hilt resolve the dependency graph at compile time via annotation processing (kapt/KSP), generating a `Dagger<Component>Impl` plus `Factory`/`Provider` classes the app calls directly with zero runtime lookup. Koin resolves at runtime: `module { }` registers lambdas in a container, and `get()` performs a type(+qualifier)-keyed lookup against that container every time it's called ([insert-koin.io](https://insert-koin.io/docs/intro/koin-vs-hilt); [Dagger GitHub](https://github.com/google/Dagger)).

**Q: What's the difference between `single`, `factory`, and `scoped`, with real examples?**
A: `single` keeps one instance for the whole container — a good fit for a `UserRepository` wrapping a shared database/network client. `factory` builds a fresh instance on every resolution — a good fit for a stateless use-case/interactor class taking per-call parameters. `scoped` builds one instance per *open scope instance*, shared while that scope is alive and discarded on `close()` — a good fit for something like session or cart state torn down on logout ([Koin Core Concepts](https://insert-koin.io/docs/intro/core-concepts); [Scopes reference](https://insert-koin.io/docs/reference/koin-core/scopes)).

**Q: `get()` vs `by inject()` — when do you use which?**
A: `get<T>()` resolves immediately and synchronously, returning `T` right away — use it inside a function body when you need the value now. `by inject<T>()` returns a `Lazy<T>` property delegate resolved on first access — Koin's own guidance is to prefer it for properties ([Retrieving Dependencies reference](https://insert-koin.io/docs/reference/koin-core/injection)).

**Q: Does Koin detect circular dependencies?**
A: Not reliably by default. A runtime cycle-detector existed in Koin 2.1.x but was removed for performance reasons, per a maintainer's own Slack comment, so a plain A→B→A cycle in the classic DSL most likely surfaces as a `StackOverflowError`. Deterministic detection today comes only from the Koin Compiler Plugin (build-time, error `KOIN-D004`) or `verify()` (test-time, `CircularInjectionException`) ([kotlinlang Slack thread](https://slack-chats.kotlinlang.org/t/499636/hello-i-m-having-this-stacktracke-while-i-m-trying-to-work-w); [Koin troubleshooting docs](https://insert-koin.io/docs/reference/koin-core/troubleshooting)).

**Q: What exception fires when a binding is missing, and is `NoBeanDefFoundException` real?**
A: Current Koin docs document `NoDefinitionFoundException` as the exception for an unresolved type. `NoBeanDefFoundException` appears across many older community threads and may be a legacy/renamed exception or a conflation with Spring's similarly-named exception — this research could not confirm its exact status, so mention both terms but commit to `NoDefinitionFoundException` as current ([Koin troubleshooting docs](https://insert-koin.io/docs/reference/koin-core/troubleshooting)).

**Q: `checkModules()` vs `verify()` — what's the difference, and which is current?**
A: `checkModules()` actually instantiates every definition in a sandboxed `koinApplication` run and is **deprecated since Koin 4.0**. `verify()` (added 3.3, extended 4.0) is a lighter, JVM-only static check of constructor-parameter types against declared definitions — no instantiation, no mocks — but it only checks constructors, missing qualifier mismatches and in-lambda `get()` calls. The Koin Compiler Plugin now layers build-time graph validation on top of both, though it doesn't cover runtime-loaded or dynamically-assembled modules ([Koin verify() docs](https://insert-koin.io/docs/4.0/reference/koin-test/verify); [Compile-Time Safety docs](https://insert-koin.io/docs/reference/koin-compiler/compile-safety)).

**Q: Is Koin "really" dependency injection, or a service locator?**
A: Mechanically it's a service locator — `get()` pulls from a registry by type at the call site. But Koin's idiomatic style confines that lookup to module definition lambdas, so application classes themselves receive plain constructor arguments and stay free of any Koin dependency — making the criticism much weaker in practice than in theory, and dependent on team discipline rather than the framework itself ([Reddit/forum discussion, search synthesis](https://redlib.hbubli.cc/r/androiddev/comments/d1b4i1/understanding_the_difference_between_di_and_sl/eznxgce)).

**Q: Why can't Dagger/Hilt be used for shared KMP code targeting iOS?**
A: Dagger relies on JVM-based annotation processing to generate factory/component code; Kotlin/Native (the iOS backend) has no equivalent processor hook, so the generated Dagger code simply doesn't exist for that target. Hilt, being Android-specific on top of Dagger, is even narrower. Koin's DSL is plain Kotlin with no codegen dependency, so it compiles identically across every KMP target ([CommonsWare community thread](https://commonsware.com/community/t/replacing-koin-with-dagger/423)).

**Q: How do you initialize Koin from Swift in a KMP app?**
A: Define `initKoin(config: KoinAppDeclaration? = null)` in `commonMain` calling `startKoin`, then add a parameterless wrapper in `iosMain` (e.g. `initKoinIos()`) because Swift can't cleanly pass a Kotlin lambda; Kotlin/Native's Objective-C export then renames the Swift call site, typically prefixing `do` (so Swift calls something like `KoinIosKt.doInitKoinIos()`) ([Koin KMP Setup docs](https://insert-koin.io/docs/reference/koin-core/kmp-setup)).

**Q: If you were starting a new Android+iOS KMP app today, which would you pick?**
A: Koin, because Dagger/Hilt cannot generate code for Kotlin/Native targets at all, making them unusable for shared DI logic. For an Android-only app, Hilt is typically preferable for its unconditional compile-time safety and official Google backing — the honest answer is "it depends on whether iOS/KMP sharing is in scope," not a universal winner ([multiple sources cited in the comparison section above]).

## What this means for building a mental model

The single idea worth anchoring every other Koin fact to is that **Koin chose to keep the dependency graph mutable and inspectable at runtime, and is now spending several release cycles buying back the compile-time safety it gave up** — first with Koin Annotations/KSP, then with the K2 Compiler Plugin, each step narrowing but never fully closing the gap with Dagger/Hilt's unconditional build-time guarantees. That trajectory also explains why so many "Koin vs Hilt" facts have an expiration date: `checkModules()` is deprecated, `koin-ksp-compiler` is deprecated, `KoinContext()`/`KoinAndroidContext()` in Compose are deprecated, and the Compiler Plugin itself moved through multiple pre-release versions during the period this research covers — so the durable interview knowledge is the *shape* of the trade-off (runtime flexibility and KMP portability versus compile-time certainty and Google backing), not any single API name or benchmark number, several of which (exact current Koin version, Wasm maturity, precise performance deltas) remain genuinely unsettled even in Koin's own ecosystem as of this writing.
